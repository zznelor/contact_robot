# Разработчику

Как устроен робот и как его дорабатывать. Код небольшой (около 2500 строк Python), без фреймворков
на фронтенде и без внешних сервисов, кроме Битрикса и Орбиты.

## Стек

- Python 3.11+, FastAPI + uvicorn, httpx
- SQLite (один файл, режим WAL) — сделки, журнал, настройки, пользователи
- Страницы панели собираются на сервере строками HTML, без JS-фреймворков и сборки
- Зависимости — [uv](https://docs.astral.sh/uv/) (`pyproject.toml`, `uv.lock`)
- Развёртывание — Docker + Caddy (HTTPS)

## Запуск для разработки

```bash
uv sync
uv run python -m first_contact run          # http://127.0.0.1:8080, база в data/state.sqlite3
DRY_RUN=1 uv run python -m first_contact run   # ничего не отправлять и не менять в Битриксе
```

Тесты — без сети, на подделках Битрикса и Орбиты:

```bash
uv run pytest -q                                   # все тесты (tests/)
uv run pytest -q tests/test_worker.py              # один файл: логика робота
uv run pytest -q tests/test_worker.py::test_steps_one_by_one   # один тест
```

У каждого теста своя временная база и свои подделки (общие — `tests/conftest.py`); `.env` и переменные
окружения машины в тесты не попадают.

## Как работает

```
Битрикс: новая сделка ──вебхук──► /bitrix/deal-add ─┐
                       ◄──опрос раз в минуту────────┤
                                                    ▼
                                         Worker.first_contact
                          ┌────────── телефоны контактов сделки ──────────┐
                          ▼                                               ▼
              Орбита POST /dialogs по каналам                    нет телефона / нигде
              (порядок из настроек, обычно WA → Max → TG)       не найден → этап
                          │                                     «Не нашёл мессенджер»
                          ▼
                     sent_first ──── клиент ответил (вебхук message.received
                          │          или опрос истории) ──► replied ──► ответ по шаблону
                   N часов тишины                                         (через паузу, один раз)
                          ▼
              напоминание (sent_followup) или no_reply
                          │
                   ещё N часов тишины (история) ──► no_reply, ответил ──► replied
```

Цикл (`Worker.tick`) раз в `POLL_SECONDS` (60 с):
0. принятые, но не обработанные события Орбиты (`orbita_events`, см. «Защита от дублей»), затем чистка
   обработанных событий и исходов отправок старше 30 дней (`cleanup`); оба шага идут и при выключенном роботе;
1. новые сделки из Битрикса после `last_deal_id` (курсор опроса, растёт);
2. `new` → первое сообщение;
3. `sent_first` с наступившим `followup_due_at` → напоминание (срок прошёл больше 48 ч назад — `no_reply`
   без напоминания, если по истории клиент не ответил); `sent_followup` через `followup_hours` после
   напоминания → по истории `replied` или `no_reply` (`Worker.after_followup`);
4. `pending_first` дольше 30 минут от `pending_at` → «проверить вручную»; `message.sent` по тому же
   `request_key`, пришедший позже, переводит такую сделку в `sent_first` (как в срок), `message.failed` —
   оставляет `needs_check` с причиной (см. «Исход отправки по `request_key`»). «Повторить» из этого состояния
   (возврат в `new`) `request_key` и `pending_at` прежней отправки не стирает: её исход, пришедший до новой
   передачи, применяется. У `pending_first` из версий до `pending_at` при
   открытии базы `pending_at` берётся из `updated_at` (момент записи ожидания). Так же — напоминание и ответ по шаблону,
   переданные с 202 (`sent_followup` с `followup_request_key`, `replied` с `reply_request_key`): дольше
   30 минут от `followup_sent_at` / `reply_sent_at` без вебхука → «проверить вручную», ключи остаются;
4а. возврат этапа сделкам, которым написали после «Повторить» (`stages`, см. «Возврат этапа»);
5. если вебхуков Орбиты нет, но включён ответ по шаблону — опрос истории свежих диалогов (раз в 5 минут
   на диалог);
6. ответы по шаблону, у которых наступил `reply_due_at`. Не уходит, если менеджер уже ответил после
   сообщения клиента или если робот опоздал больше чем на 30 минут (`REPLY_MAX_LATE`) от момента, когда должен
   был ответить: первое сообщение клиента по истории + пауза `reply_delay_minutes`, а после ручного
   «Повторить» — момент повтора (`reply_retried_at`), если он позже. Эти проверки — для новой отправки. Есть
   незавершённая (намерение `reply_key` сохранено, а ответа 201 / 202 нет) — история не читается, сразу повтор тем
   же ключом и текстом: в истории уже может быть сам этот ответ исходящим после сообщения клиента, а история не
   отличает робота от менеджера, и «менеджер уже ответил» навсегда отменило бы выяснение исхода. Граница повтора —
   48 часов от `reply_due_at` / `reply_retried_at`, что позже (позже повтор мог бы стать отправкой спустя двое
   суток): за ней — `needs_check` («исход неизвестен»), а не молчаливая отмена.

Шаги перечислены в `Worker.STEPS`. Панель запускает весь проход (`tick`) или один шаг (`run_step`) через
`POST /actions/tick` с полем `step` (`all` или ключ шага). Шаг «ответы в истории», запущенный вручную, работает
и при настроенных вебхуках и не ждёт 5-минутную паузу.

Вебхуки — ускорение, а не замена: события теряются, опрос — нет.

### Замок и ручные действия

`Worker.lock` — один замок на состояние сделок и флаг «включён». Под ним идут: шаг робота по **одной**
сделке (`_guarded`: от проверки статуса до записи результата, вместе с вызовами Битрикса и Орбиты),
события Орбиты, ручные действия панели (`Worker.stop`, `mark_replied`, `retry`, `take`) и
`enable` / `disable`. Поэтому:
- ручное действие ждёт только шаг по текущей сделке (обычно секунды), а не весь проход;
- когда кнопка «Остановить» / «Клиент ответил» / «Выключить» ответила, робот по этой сделке (по всем
  сделкам) больше ничего не отправит и не перезапишет статус. Исход отправки, переданной до нажатия (202), решение не отменяет
  (`manual_stop_at`, см. «Защита от дублей»). Отправка, которая уже шла в момент нажатия,
  завершается — её результат записывается, затем применяется решение человека;
- каждый шаг под замком заново проверяет, что робот включён и настроен (`Worker.active`), и перечитывает
  сделку, — выключение посреди прохода останавливает оставшуюся очередь.

Проходы целиком (`tick`, `run_step`) не идут одновременно — у них свой замок `_pass`.

Эти замки — внутри одного процесса. Между процессами — файловый замок `db.service_lock` на `<база>.lock` рядом с
базой (POSIX — `fcntl.flock`, Windows без Docker — `msvcrt.locking`; выбор — по наличию модуля): сервис `run` держит его, пока работает, `once` и `process` — на время своей
работы. Занят — команда не запускается (код выхода 1, «остановите сервис или нажмите кнопку в панели»):
второй процесс со своим `Worker` отправлял бы и писал статусы мимо замка сервиса. `restore` берёт тот же замок
(занят — код 1 и подсказка остановить сервис): подменённая под работающим сервисом база продолжила бы его проход на
чужом состоянии. `check`, `backup` и команды пользователей замок не берут.

### Вход и смена пароля

Пароль при входе проверяется в потоке (`Users.login_async`, scrypt), и за это время пароль могут сменить — в
панели или `reset-password` из другого процесса. Смена (`Users.set_password`) пишет новый хэш и закрывает все
сессии пользователя одной транзакцией. Вход после проверки перечитывает пользователя и сверяет хэш, а сессию
создаёт условной записью — только если хэш, по которому проверен пароль, всё ещё действует
(`new_session(..., pw_hash=…)`). Поэтому вход старым паролем, начатый до смены, либо создаёт сессию до неё (её
закроет смена), либо не создаёт вовсе: «Неверная почта или пароль».

### Статусы сделки (`deals.status`)

| Статус | Значение |
|---|---|
| `new` | увидели, ещё не написали (или упали и повторим) |
| `pending_first` | Орбита ответила 202 (`pending_at`): сообщение могло уйти, ждём вебхук `message.sent` / `message.failed`. На `message.sent` `first_sent_at` — время отправки из события (нет — `pending_at`); если клиент уже написал в этот диалог (`message.received`, принятый после `pending_at`, пока номер диалога был неизвестен), — сразу `replied`. Исход и эта сверка —
одна транзакция до комментариев и возврата этапа: повтор события после обрыва ничего не теряет |
| `sent_first` | первое сообщение ушло, ждём ответа |
| `sent_followup` | напоминание ушло; через `followup_hours` — итог `replied` или `no_reply` |
| `replied` | клиент ответил; поля `reply_due_at` / `reply_sent_at` — ответ по шаблону |
| `no_reply` | не ответил: напоминание выключено или клиент молчит и после него |
| `no_messenger`, `no_phone` | этап сделки сменён на «Не нашёл мессенджер» |
| `skipped` | сделка закрыта, другая воронка, старше 48 ч, удалена в Битриксе или остановлена вручную |
| `needs_check` | не уверены, ушло ли сообщение, или Орбита сообщила, что сообщение не доставлено (`message.failed`) — нужен человек; робот не повторяет |
| `error` | 5 ошибок подряд или ошибка Битрикса, которую повтор не исправит (нет прав, вебхук удалён), — нужен человек. Счётчик `attempts` и пауза `next_attempt_at` обнуляются, когда сделка сменила статус, — той же записью, что ставит новый статус (`DB.update`), откуда бы ни пришёл переход: шаг робота, вебхук, опрос ответов, кнопка |

Сбой шага по сделке (Битрикс или Орбита недоступны, отказ Орбиты) — попытка: `attempts` растёт, следующая —
не раньше `next_attempt_at` (пауза 2, 4, 8, 16 минут — `RETRY_PAUSE`), пятая подряд → `error`. Если Орбита
назвала срок — 429 с `Retry-After`, `idempotency_in_progress` с `Retry-After`, `telegram_flood_wait` с
`retry_after`, суточный лимит `daily_send_limit_exhausted` (до полуночи UTC) или `telegram_search_limit_exhausted`
(до полуночи UTC — момент сброса в спецификации не назван, это допущение), — сделка ждёт этот срок, попытка
не тратится (в журнале «отложено»). При «не найден» в одних каналах и сроке в других срок берётся ближайший,
если его назвали все непроверенные каналы. Так же — ошибки лимитов Битрикса (`bitrix.LIMIT_CODES`,
`_includes/system-errors.md` и `settings/performance/limits.md` документации Битрикса): `QUERY_LIMIT_EXCEEDED`
(интенсивность запросов ко всему порталу, общая для приложений с одного IP) — нарастающая задержка 1, 2, 4 … минут,
не больше 30 сколько угодно долго подряд (`LIMIT_PAUSE`, `LIMIT_PAUSE_MAX`; показатель удвоения
ограничен `LIMIT_DOUBLINGS`; успешный ответ сбрасывает рост); `OPERATION_TIME_LIMIT`
(ресурсоёмкость одного метода) — до `time.operating_reset_at` из этого ответа или из последнего успешного ответа того
же метода, а если срок уже прошёл и ошибка повторилась — та же нарастающая задержка. До срока клиент `Bitrix` в
портал не ходит (весь портал при `QUERY_LIMIT_EXCEEDED`, один метод при `OPERATION_TIME_LIMIT`) и сразу отвечает
той же ошибкой со сроком: остальные сделки прохода портал не дёргают. Срок и рост задержки — в памяти клиента:
перезапуск или смена адреса вебхука начинают с минуты. Возврат этапа (`_restore_stage`) по ошибке лимита тоже
ждёт срок, не тратя попытку (`stage_retry_at`).

Ошибки Битрикса, которые повтором не исправить (`BitrixError.permanent`: коды `bitrix.PERMANENT_CODES` — нет
доступа, вебхук не найден или без scope, метода нет, портал закрыт, `OVERLOAD_LIMIT` — ручная блокировка
поддержкой; у ошибок уровня метода с пустым кодом — описание «Not found» / «Access denied»), не ждут пяти пауз:
сразу `error` с причиной «повтор не поможет» в `last_error`, комментарий в сделку (проверить права пользователя
вебхука). Сделки нет в Битриксе («Not found» у `crm.deal.get` / `crm.deal.update` /
`crm.deal.contact.items.get` — `BitrixError.deal_missing`) — `skipped` «сделки нет в Битриксе», без комментария:
оставить его некуда. Описание с другим текстом (перевод, новая формулировка) — обычный сбой с повторами: принять
временный сбой за окончательный хуже, чем пять раз повторить окончательный. Возврат этапа при такой ошибке
сдаётся сразу — комментарий «верните вручную». Сбой одного шага прохода (например, опроса Битрикса) пишется
в лог и не отменяет остальные шаги.

«Повторить» в панели — `Worker.retry()`: статус `new`, если первое сообщение не ушло (`first_sent_at` пусто),
иначе `sent_first` / `sent_followup` / `replied` — с того места, где робот остановился. Номер повтора шага, с которого
продолжает робот, растёт и входит в ключ идемпотентности (см. «Защита от дублей»). При возврате в `new`
растёт `retry_n`, пишется `retried_at` (48 ч считаются от более позднего из `created_at` и `retried_at`), а
проверка этапа «Не нашёл мессенджер» в `first_contact` пропускается — этот этап ставил сам робот.

Возврат этапа. Перенося сделку на «Не нашёл мессенджер» (`_no_messenger`), робот запоминает её этап до
переноса в `stage_before` — до вызова Битрикса, чтобы обрыв между переносом и записью статуса не потерял
прежний этап (если сделка уже стояла на этом этапе — прежнее значение не затирается; сделка `new` с
`stage_before` на этом этапе — перенос робота, а не менеджера, и он не мешает следующей попытке). Когда
после «Повторить» первое сообщение ушло (201 или `message.sent` по 202), `_restore_stage` перечитывает
сделку: она всё ещё на «Не нашёл мессенджер» — возвращает на `stage_before`, комментарий в ленту; менеджер
уже сам перенёс её на другой этап — не трогает. `stage_before` пуст (сделка перенесена версией до
22.10.2026) — этап не трогается. Возврат — сохранённая работа: пока `stage_before` не пуст при заполненном
`first_sent_at`, его доделывает шаг прохода `stages` (после перезапуска и после сбоя Битрикса — с паузой
2, 4, 8, 16 минут, `stage_attempts` / `stage_retry_at`). Отправка при этом не повторяется. Пятый сбой
подряд — запись в журнал, комментарий «верните вручную», `stage_before` стирается.

### Защита от дублей

- У каждой отправки в Орбиту есть `Idempotency-Key` (`deal-<id>-first-<телефон>[-r<retry_n>]-<канал>`,
  `deal-<id>-followup[-r<followup_retry_n>]`, `deal-<id>-reply[-r<reply_retry_n>]`). Повтор с тем же ключом
  не отправит сообщение второй раз. Поэтому обрыв связи с Орбитой — обычная повторяемая ошибка. Ручной
  «Повторить» добавляет `-r<n>` к ключу того шага, с которого робот продолжит: первое сообщение (`retry_n`,
  возврат в `new`), напоминание (`followup_retry_n`, возврат в `sent_first`), ответ по шаблону
  (`reply_retry_n`, возврат в `replied`, если ответ не ушёл, — он планируется заново). Это новая отправка:
  со старым ключом Орбита вернула бы прежний исход, а при изменённом шаблоне — `idempotency_key_reused`.
  Ключи сделок, начатых до обновления, не меняются (номера повторов шагов — 0).
- Намерение напоминания и ответа по шаблону — ключ и текст (`followup_key` + `followup_text`, `reply_key` +
  `reply_text`): пишутся до запроса и стираются только при определённом отказе (отказ Орбиты 4xx, `message.failed`).
  Исход неизвестен (сбой связи, 5xx, непредвиденный сбой, 202 без подтверждения) — намерение остаётся, и
  следующая отправка шага, в том числе после «Повторить», идёт **тем же** ключом и **тем же** текстом, даже если
  шаблон или название сделки с тех пор поменялись: если прошлое сообщение дошло, Орбита второе не отправит.
  Новый `-r<n>` «Повторить» выпускает, только когда ключа нет — прошлая попытка точно не ушла или Орбита отвергла
  ключ (`idempotency_key_reused`, ниже). Ключ, сохранённый
  версией без текста, повторяется с текстом, собранным заново, и этот текст запоминается.
- `idempotency_key_reused` (422: ключ уже приходил с другим телом) — не отказ: прежний запрос с этим ключом мог
  отправить сообщение (`OrbitaAPIError.definite` ложно), сделка — `needs_check`, как при неизвестном исходе. Но
  исход нашего тела такой ключ не вернёт никогда — ключ «сожжён». У напоминания и ответа по шаблону намерение
  (`*_key`, `*_text`) снимается той же записью, что ставит `needs_check` (`UnknownOutcome.fields`), и пишется
  `reused_key_step` — шаг, чей ключ отвергнут: панель предупреждает у «Повторить» о возможном втором сообщении,
  «Повторить» снимает отметку и идёт новым `-r<n>`. Номер растёт при «Повторить» по общему правилу для любого
  снятого ключа (ключа нет — новый `-r<n>`), а не в записи `needs_check`: иначе он вырос бы дважды. У первого
  сообщения правило то же: «Повторить» из `needs_check` снимает намерение и идёт новым `-r<n>`, панель
  предупреждает (`needs_check` без `first_sent_at`).
- 202 на напоминание и ответ по шаблону (для WhatsApp и Max — обычный ответ: «команда передана») — сообщение
  могло уйти, исход придёт вебхуком. `OrbitaAPI.send_reply` возвращает статус и `request_key`; он
  сохраняется в `followup_request_key` / `reply_request_key` до вебхука. Как исход применяется — «Исход отправки
  по `request_key`» ниже: `message.sent` — ключ стирается, в журнале «мессенджер подтвердил доставку».
  `message.failed` — шаг не сделан: `needs_check`, причина в
  `last_error` и журнале, комментарий в сделку; `followup_sent_at` / `reply_sent_at` стираются, у ответа
  по шаблону `reply_due_at` остаётся (ответ ещё нужен). Так же — из `needs_check` по таймауту и из
  `no_reply`: итог «не ответил» по недоставленному напоминанию снимается (если в нём учтено это напоминание —
  `followup_sent_at` не пуст). Пришёл, когда клиент уже ответил
  или сделку остановили, — статус не меняется, записываются только поля доставки и журнал. Остановка — признак `manual_stop_at` («Остановить робота»,
  «Клиент ответил»; «Повторить» его снимает): у такой сделки ни поздний исход, ни таймаут подтверждения
  (`send_timeout`) не ставят «проверить вручную» и не планируют ответ заново. Пока напоминание не подтверждено, итог «не ответил»
  (`after_followup`) не выносится. Вебхука нет 30 минут — `needs_check` (`Worker.send_timeout`), ключи
  остаются: `message.received` в диалоге сделки, которая так ждёт подтверждения напоминания (первое сообщение
  подтверждено, клиент ещё не отвечал), — ответ клиента, как в `sent_followup`; поздний `message.sent` возвращает
  сделку в `sent_followup` / `replied`, а «Повторить» снова
  отправляет шаг **тем же** ключом (Орбита вернёт исход прошлого запроса, второго сообщения не будет).
  `followup_request_key` / `reply_request_key` прежней отправки «Повторить» не стирает: исход, пришедший между
  кнопкой и повтором, применяется — `message.sent` засчитывает шаг (`sent_followup` / ответ отправлен, повтора нет),
  `message.failed` — прежняя отправка точно не ушла, повтор идёт новым `-r<n>`.
  Поэтому без вебхуков каждое напоминание и ответ по шаблону, на которые Орбита ответила 202, через 30
  минут становятся «проверить вручную» — как и первое сообщение.
- Вебхуки Орбиты — durable inbox. Для Орбиты ответ 2xx значит «доставлено», повтора не будет, поэтому
  `/orbita/webhook` до ответа сохраняет событие целиком в `orbita_events` (`state='new'`, номер события —
  ключ дедупликации; повтор доставки с тем же номером отвечает `duplicate`). Событие без номера
  сохраняется под своим (`local-…`). Обработка — `Worker.process_inbox()`: сразу в фоне и на каждом
  проходе (шаг `events`, идёт и при выключенном роботе). `done` ставится только после успешной обработки;
  сбой пишется в журнал («Орбита: ошибка обработки события») и в лог, событие остаётся в очереди до
  следующего прохода, после 5 сбоев — `failed`. Остановка сервиса посреди обработки оставляет событие
  в очереди — его подхватит первый проход после запуска. Обработка идемпотентна: каждое действие
  проверяет статус сделки. Строки старых версий (без тела) при обновлении считаются `done`. Обработанные
  (`done`) события старше 30 дней (`EVENTS_KEEP`, по `done_at`, у старых строк — по `at`) удаляет шаг
  `cleanup`: дубли доставки и сверка ответа клиента до подтверждения первого сообщения смотрят только
  недавние события. `new` и `failed` не удаляются. Индексы `orbita_events` — `db.INDEXES`, создаются после
  `MIGRATIONS`.
- Намерение первой отправки. Каналы перебирает сам робот (`Worker.first_contact`, по телефонам и по
  порядку каналов из настроек; клиент Орбиты — `OrbitaAPI.start_dialog`, один канал за запрос). Перед
  каждым `POST /dialogs` в сделку пишется намерение: `intent_phone`, `intent_channel`, `intent_key`;
  стирается оно, когда исход определён — ответ 201/202/«не найден»/«не проверен»/400 или отказ 4xx, по
  которому точно ничего не ушло. На 201/202 намерение стирается той же записью, что ставит `sent_first` /
  `pending_first`: обрыв процесса между ними не оставит сделку `new` без намерения. Сбой связи, 5xx и `idempotency_in_progress` намерение оставляют, и
  следующая попытка сначала повторяет **тот же** запрос целиком (канал, номер, ключ, текст `first_text` и имя
  `name` — оба записаны той же попыткой до запроса; свежее имя из Битрикса в повтор не попадает): Орбита вернёт
  исход первого вызова, а с другим телом ответила бы `idempotency_key_reused`. Канал намерения сейчас не подключён → `needs_check` (в другой канал писать нельзя —
  клиент получит два первых сообщения). Повтор намерения (`Worker._resume_first`) идёт **до** решений по свежим
  данным Битрикса — воронки, этапа, контактов и телефонов, ожидания телефона: это завершение уже переданной
  отправки, а не новая, и её исход (в том числе принятый раньше ключа, см. «Исход отправки по `request_key`»)
  сопоставляется, даже если менеджер тем временем отвязал контакт или закрыл сделку. До повтора проверяется только
  то, что запрещает сам повтор (не получив первый запрос, Орбита отправит по повтору впервые): сделка в `new`
  (ручная остановка и пропуск её оттуда уводят), окно отправки (вне окна сделка ждёт) и 48 часов — по
  `created_at` / `retried_at`, без запроса в Битрикс: за 48 ч повтора нет, сделка не пропускается, а уходит в
  `needs_check` («исход неизвестен, заявка старше 48 ч»). Исход определён и сообщение не ушло (не найден, номер не
  принят, отказ 4xx) — намерение снято, дальше обычная новая отправка со всеми проверками. «Повторить» из `needs_check` намерение стирает: человек проверил
  переписку, панель предупреждает о втором сообщении.
- Неизвестный исход (`UnknownOutcome`) → `needs_check`, без повтора.
- «Номера нет в мессенджере» — только если **все** выбранные каналы ответили «не найден». Выбранный, но не
  подключённый канал номер не проверял; он, как и канал, не смогший проверить номер (лимит, сбой шлюза),
  даёт ошибку с повтором, а не перенос на этап.
- Орбита не приняла номер (400 `invalid_request` на «написать первым») — номер пропускается, пробуется
  следующий телефон; не принят ни один — как «нет телефона» (`no_phone`, этап «Не нашёл мессенджер»).
- Телефоны — всех контактов сделки (`Bitrix.deal_contacts`: `crm.deal.contact.items.get`, главный контакт —
  `IS_PRIMARY`, — первым, затем по `SORT` привязки; поле сделки `CONTACT_ID` в документации «Устаревшее»), по
  порядку контактов, номер, встретившийся у нескольких, — один раз. Имя для `{name}` и поля `name` запроса — того
  контакта, у которого номер встретился первым: оно и текст (`name`, `first_text`) пишутся той же записью, что
  намерение отправки на этот номер (`Worker._start`), поэтому повтор после неизвестного исхода несёт имя своего
  номера. Ключ идемпотентности — с номером, как раньше. Компания сделки не читается.
- Телефона нет ни у одного контакта (или контактов нет) — сделка не сразу `no_phone`: источник заявки может
  создать сделку и привязать контакт следующим вызовом, а `ONCRMDEALADD` приходит при создании. Пока с появления
  сделки (`DATE_CREATE`, нет её — `created_at`, момент, когда робот увидел сделку) прошло меньше `PHONE_WAIT`
  (10 минут), сделка остаётся `new` и перечитывается на каждом проходе; попытки не тратятся, этап не меняется,
  в `last_error` и журнале — «ждём телефон» до какого времени (в журнал — один раз). Прошло — `no_phone` и этап
  «Не нашёл мессенджер», как раньше. Ручной «Повторить» и «Взять в работу» старой сделки без телефона получают
  `no_phone` сразу: отсчёт — от создания сделки, а не от нажатия. 48 часов проверяются раньше и не меняются.
- Сделки старше 48 часов не трогаем. Возраст — от `DATE_CREATE` сделки в Битриксе (пока Битрикс не
  спрошен или даты нет — от `created_at`, момента, когда робот увидел сделку) или от ручного повтора /
  «Взять в работу» (`retried_at`), что позже. Сделка с незавершённой отправкой (намерение) старше 48 часов не
  пропускается, а уходит в `needs_check` (см. «Намерение первой отправки»).
- Граница включения `kv.start_deal_id` — последняя сделка Битрикса в момент включения; не меняется до
  следующего включения (в отличие от курсора опроса `last_deal_id`). Событие Битрикса о сделке, которой
  нет в базе и чей ID не больше границы, робот пропускает: она создана до включения. «Взять в работу» в
  панели (`Worker.take`) — явный путь, граница ему не мешает. Установкам, включённым до появления границы,
  она при запуске берётся из `last_deal_id`.

### Исход отправки по `request_key`

На ответ 202 («передано») Орбита присылает исход отправки вебхуком `message.sent` / `message.failed` с её
`request_key`. Первое сообщение, напоминание и ответ по шаблону сопоставляются с исходом **одним механизмом и
по ключу, а не по статусу сделки** (`Worker._send_outcome`, `_handed_over`, `_match_outcome`, `_apply_first`,
`_apply_step`):

- Ключ отправки шага, ждущей исхода, — `request_key` (первое), `followup_request_key`, `reply_request_key`
  (`DB.SEND_KEYS`). Пишется на 202, снимается, когда исход применён.
- Вебхук с исходом сохраняется в `send_outcomes` (последний исход по ключу) и той же транзакцией применяется к
  отправке, чей ключ уже записан в сделку. Ключа нет ни у одной сделки (ответ 202 до робота не дошёл, процесс
  оборвался до записи ответа) — исход остаётся неприменённым (`applied_at` пуст): это сохранённая работа, а не
  потерянное событие (`orbita_events` при этом `done`).
- Запись ключа любой отправки (`_handed_over`) — одна транзакция со сверкой с `send_outcomes`. Повтор запроса
  тем же `Idempotency-Key` после потерянного ответа снова получает 202 с тем же `request_key` — и сразу исход,
  принятый раньше, без ожидания ещё одного вебхука и без «проверить вручную» по таймауту.
- **Факт** записывается по ключу в любом статусе. `message.sent` первого — `first_sent_at` (момент из события,
  иначе `pending_at`), `dialog_id`, `followup_due_at`, намерение снято; напоминания / ответа — `followup_sent_at`
  / `reply_sent_at`, если пусты (у ответа снимается и `reply_due_at`). `message.failed` первого — снимаются
  `request_key` и `pending_at`; напоминания / ответа — шаг не сделан: стираются `*_sent_at` и намерение (`*_key`,
  `*_text`), «Повторить» пойдёт новым `-r<n>`; у ответа без ручной остановки `reply_due_at` ставится снова (ответ
  ещё нужен).
- **Статус** меняется только там, где робот ещё ждёт этот шаг, и никогда при ручном решении (`manual_stop_at`:
  «Остановить робота», «Клиент ответил») — тогда только факт и запись в журнал («статус … не меняется»):

  | Шаг | `message.sent` | `message.failed` → `needs_check` |
  |---|---|---|
  | первое | → `sent_first` из `pending_first`, `needs_check`, `new` («Повторить» нажат, новая попытка не передана), `error`; клиент уже писал в диалог — сразу `replied` | из `pending_first`, `needs_check` |
  | напоминание | → `sent_followup` из `needs_check`, `error`, `sent_first` («Повторить» нажат, повтор не ушёл); после ответа клиента — нет | из `sent_followup`, `needs_check`, `no_reply` (итог учитывал это напоминание) |
  | ответ по шаблону | → `replied` из `needs_check`, `error` | из `replied`, `needs_check` |

  Комментарии в сделку и возврат этапа «Не нашёл мессенджер» — после транзакции. Возврат этапа — при любом
  статусе, если факт доставки первого записан: этап больше не правда.
- «Повторить» ключ прежней отправки не стирает ни у одного шага: её исход, пришедший между кнопкой и повтором,
  применяется. Первое сообщение после возврата в `new` уходит новым ключом `-r<n>`; новая передача (202)
  заменяет `request_key`, ответ 201 его снимает. Исход отправки, вытесненной новой, сделку не меняет.
- Исходы хранятся 30 дней по моменту приёма (`EVENTS_KEEP`), удаляет шаг `cleanup`: исход тестового сообщения
  из настроек или чужой отправки тем же ключом API свою отправку не найдёт никогда.

Инварианты (`tests/test_send_outcome.py` — по каждому шагу и пути: вебхук до и после записи ключа, после
«Остановить», после «Клиент ответил», из `needs_check`, из `error`, после «Повторить»):
- подтверждённая доставка первого сообщения ⇒ `first_sent_at` заполнен в любом статусе;
- `sent_followup` ⇒ `followup_sent_at` заполнен; доказанный отказ ⇒ `*_sent_at` шага пуст в любом статусе;
- исход применён ⇒ ключ шага снят;
- «Повторить» после подтверждённой доставки шаг не повторяет, после доказанного отказа — повторяет новым ключом.

В панели подсказка «Повторить» о возможном втором первом сообщении — у сделки, где первое не подтверждено:
`needs_check` или ключ первой отправки ждёт исхода (`request_key` при пустом `first_sent_at`), в любом статусе.

## Настройки

- `Env` (`config.env()`) — из переменных окружения / `.env`: `DB_PATH`, `PUBLIC_URL` или `DOMAIN`, `PORT`,
  `POLL_SECONDS`, `DRY_RUN`, `HOST` (по умолчанию `127.0.0.1`), `FORWARDED_ALLOW_IPS` (чьим `X-Forwarded-*`
  верить, по умолчанию `127.0.0.1`). В Docker-образе `HOST=0.0.0.0` и `FORWARDED_ALLOW_IPS=*`: порт контейнера
  открыт только для самого сервера, снаружи — только через Caddy.
- Воронка: `Settings.category` — выбранная воронка или `"0"` (основная), если не выбрана. Робот работает
  только с ней.
- `Settings` (`config.load(db)`) — из таблицы `settings` (ключ → JSON). Меняются в панели через
  `worker.save(**поля)`: значение пишется в базу и сразу действует. Если меняется адрес Битрикса или ключ
  Орбиты, клиенты пересоздаются (`worker.reconnect()`).

Чтобы добавить настройку: поле в `Settings` со значением по умолчанию → поле формы в `ui_settings.py` →
использование в `worker.py`. Миграция не нужна: отсутствующий ключ берётся из значения по умолчанию.

При самом первом запуске, если в базе нет настроек, `config._seed_from_env()` берёт их из старых
переменных окружения (`BITRIX_WEBHOOK`, `ORBITA_API_KEY`, …) — для установок, настроенных до панели.

## База

Схема — `db.SCHEMA`, новые колонки — список `db.MIGRATIONS` (добавляются при запуске сами).
Чтобы добавить колонку в существующую таблицу, допишите строку в `MIGRATIONS`.

## Как подключить другую CRM

`Worker` вызывает у `self.bitrix` только эти методы:

```python
async def get_deal(deal_id: int) -> Deal            # Deal: id, title, stage_id, stage_semantic ("P" — в работе),
                                                     #       category_id, created_at (aware или None)
async def deal_contacts(deal_id: int) -> list[Contact]   # все контакты сделки, главный первым, затем по порядку;
                                                     # Contact: id, name, phones (в виде +7…, без дублей)
async def deal_ids_after(last_id: int, category_id: str | None) -> list[int]   # новые сделки по возрастанию
async def max_deal_id() -> int
async def set_stage(deal_id: int, stage_id: str) -> None
async def comment(deal_id: int, text: str) -> None
```

Для страницы настроек — ещё `categories()` и `stages(category_id)` (списки пар `(id, название)`; `stages` — только
этапы **в работе**, у Битрикса `SEMANTICS` не `S` и не `F`). Этап «Не нашёл мессенджер» выбирается только из них:
форма с закрывающим этапом (в том числе подделанная) не сохраняется, сохранённый старой версией закрывающий или
удалённый этап страница настроек показывает как ошибку настройки, а «Включить робота» его не включает
(`ui_settings.stage_problem`, `enable`). Включённый робот при этом сам не выключается: остальные сделки он ведёт
верно, а перенос на этот этап — только у сделок без мессенджера; решение — за владельцем.
Списочные методы Битрикса отдают по 50 строк. Новые сделки (`deal_ids_after`) читаются по рекомендации
`settings/performance/huge-data.md` документации Битрикса: `order ID ASC`, фильтр `>ID` последнего полученного ID,
`start=-1` (без подсчёта `total`), повтор, пока страница полная. Смещение (`start`/`next`) здесь теряло бы
сделку: удаление уже отданной сделки или потеря прав на неё между запросами страниц сдвигает выборку, а курсор
опроса `last_deal_id` уходит дальше пропущенной. Курсор двигается только по ID, которые опрос реально получил;
сбой на любой странице не двигает его вовсе — следующий опрос перечитает. Этапы (`stages`) читает `Bitrix.call_all`
по `next`: у `crm.status.list` в документации нет ни `start`, ни фильтра `>ID`, этапов в воронке единицы-десятки
(одна страница), а этап, пропущенный из-за удаления между страницами, только не попадёт в список панели до
обновления страницы — сохранение этапа проверяет его по свежему списку. Воронки (`categories`) — один запрос:
у `crm.category.list` параметров страниц нет.

Чтобы подключить, например, amoCRM:
1. Напишите класс с этими методами (`src/first_contact/amocrm.py`).
2. В `Worker.reconnect()` выберите класс по настройке (например, `crm = "bitrix" | "amocrm"`).
3. Добавьте приём вебхука новой сделки в `app.py` по образцу `/bitrix/deal-add`.
4. Добавьте блок настроек в `ui_settings.py`.

В amoCRM ID сделок тоже растут, так что опрос по `last_deal_id` подходит.

## Как добавить свой шаг

Пример: «двигать сделку на этап „Написали“ после первого сообщения».
1. `config.Settings`: `stage_after_first: str = ""`.
2. `worker._mark_sent_first`: `if self.s.stage_after_first: await self.bitrix.set_stage(...)`.
   Метод синхронный — вызывайте из `first_contact` после `_mark_sent_first`.
3. `ui_settings.bitrix_section`: ещё один `<select>` с этапами, сохранение в `save_bitrix`.
4. Тест в `tests/test_worker.py`.

## API Орбиты

Публичная спецификация: `https://crm.my-orbita.ru/api/public/v1/openapi.json` (копия в `docs/`).

Что использует робот:
- `GET /account`, `GET /channels`;
- `POST /dialogs` — «написать первым» (по одному каналу за запрос);
- `POST /dialogs/{id}/messages` — ответ в диалог;
- `GET /dialogs/{id}/messages` — история (только направление и время, без текста). Лента — новые первыми,
  страницами по `next_cursor`; `OrbitaAPI.history(dialog, since)` читает страницы, пока не дойдёт до
  `since` (первое сообщение робота) с запасом `CLOCK_SKEW`. Время без смещения считается UTC.
  Сообщение без `sent_at` нельзя расположить относительно первого сообщения: ответом клиента оно не
  считается, молчанием тоже. Если кроме него входящих после первого нет — «не понять»
  (`client_replied` → `None`): напоминание не уходит, сделка — `needs_check`;
- вебхуки, подпись `X-Orbita-Signature: v1=HMAC-SHA256(секрет, "<timestamp>.<тело>")`.

Коды «номера нет»: `not_on_whatsapp`, `max_not_found`, `telegram_recipient_not_found`,
`telegram_recipient_refused`.

Лимиты: 600 запросов в минуту и 1000 отправок в сутки на ключ, поиск в Telegram — 30 номеров в сутки
на сотрудника.

MCP Орбиты робот не использует: «написать первым» есть только в REST API.
