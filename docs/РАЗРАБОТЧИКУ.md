# Разработчику

Как устроен робот и как его дорабатывать. Код небольшой (около 2500 строк Python), без фреймворков
на фронтенде и без внешних сервисов, кроме Битрикса и Орбиты.

## Стек

- Python 3.11+, FastAPI + uvicorn, httpx
- SQLite (один файл, режим WAL) — сделки, журнал, настройки, пользователи
- Страницы панели собираются на сервере строками HTML, без JS-фреймворков и сборки
- Зависимости — [uv](https://docs.astral.sh/uv/) (`pyproject.toml`, `uv.lock`)
- Развёртывание — Docker + Caddy (HTTPS)

## Запуск для разработки

```bash
uv sync
uv run python -m first_contact run          # http://127.0.0.1:8080, база в data/state.sqlite3
DRY_RUN=1 uv run python -m first_contact run   # ничего не отправлять и не менять в Битриксе
```

Тесты — без сети, на подделках Битрикса и Орбиты:

```bash
uv run pytest -q                                   # все тесты (tests/)
uv run pytest -q tests/test_worker.py              # один файл: логика робота
uv run pytest -q tests/test_worker.py::test_steps_one_by_one   # один тест
```

У каждого теста своя временная база и свои подделки (общие — `tests/conftest.py`); `.env` и переменные
окружения машины в тесты не попадают.

## Как работает

```
Битрикс: новая сделка ──вебхук──► /bitrix/deal-add ─┐
                       ◄──опрос раз в минуту────────┤
                                                    ▼
                                         Worker.first_contact
                          ┌───────────── телефон из контакта ─────────────┐
                          ▼                                               ▼
              Орбита POST /dialogs по каналам                    нет телефона / нигде
              (порядок из настроек, обычно WA → Max → TG)       не найден → этап
                          │                                     «Не нашёл мессенджер»
                          ▼
                     sent_first ──── клиент ответил (вебхук message.received
                          │          или опрос истории) ──► replied ──► ответ по шаблону
                   N часов тишины                                         (через паузу, один раз)
                          ▼
              напоминание (sent_followup) или no_reply
                          │
                   ещё N часов тишины (история) ──► no_reply, ответил ──► replied
```

Цикл (`Worker.tick`) раз в `POLL_SECONDS` (60 с):
0. принятые, но не обработанные события Орбиты (`orbita_events`, см. «Защита от дублей»), затем чистка
   обработанных старше 30 дней (`cleanup`); оба шага идут и при выключенном роботе;
1. новые сделки из Битрикса после `last_deal_id` (курсор опроса, растёт);
2. `new` → первое сообщение;
3. `sent_first` с наступившим `followup_due_at` → напоминание (срок прошёл больше 48 ч назад — `no_reply`
   без напоминания, если по истории клиент не ответил); `sent_followup` через `followup_hours` после
   напоминания → по истории `replied` или `no_reply` (`Worker.after_followup`);
4. `pending_first` дольше 30 минут от `pending_at` → «проверить вручную»; `message.sent` по тому же
   `request_key`, пришедший позже, переводит такую сделку в `sent_first` (как в срок), `message.failed` —
   оставляет `needs_check` с причиной. «Повторить» из этого состояния (возврат в `new`) стирает `request_key`
   и `pending_at`: прежняя отправка больше исхода не ждёт. Так же — напоминание и ответ по шаблону,
   переданные с 202 (`sent_followup` с `followup_request_key`, `replied` с `reply_request_key`): дольше
   30 минут от `followup_sent_at` / `reply_sent_at` без вебхука → «проверить вручную», ключи остаются;
4а. возврат этапа сделкам, которым написали после «Повторить» (`stages`, см. «Возврат этапа»);
5. если вебхуков Орбиты нет, но включён ответ по шаблону — опрос истории свежих диалогов (раз в 5 минут
   на диалог);
6. ответы по шаблону, у которых наступил `reply_due_at`. Не уходит, если менеджер уже ответил после
   сообщения клиента или если робот опоздал больше чем на 30 минут (`REPLY_MAX_LATE`) от момента, когда должен
   был ответить: первое сообщение клиента по истории + пауза `reply_delay_minutes`, а после ручного
   «Повторить» — момент повтора (`reply_retried_at`), если он позже.

Шаги перечислены в `Worker.STEPS`. Панель запускает весь проход (`tick`) или один шаг (`run_step`) через
`POST /actions/tick` с полем `step` (`all` или ключ шага). Шаг «ответы в истории», запущенный вручную, работает
и при настроенных вебхуках и не ждёт 5-минутную паузу.

Вебхуки — ускорение, а не замена: события теряются, опрос — нет.

### Замок и ручные действия

`Worker.lock` — один замок на состояние сделок и флаг «включён». Под ним идут: шаг робота по **одной**
сделке (`_guarded`: от проверки статуса до записи результата, вместе с вызовами Битрикса и Орбиты),
события Орбиты, ручные действия панели (`Worker.stop`, `mark_replied`, `retry`, `take`) и
`enable` / `disable`. Поэтому:
- ручное действие ждёт только шаг по текущей сделке (обычно секунды), а не весь проход;
- когда кнопка «Остановить» / «Клиент ответил» / «Выключить» ответила, робот по этой сделке (по всем
  сделкам) больше ничего не отправит и не перезапишет статус. Отправка, которая уже шла в момент нажатия,
  завершается — её результат записывается, затем применяется решение человека;
- каждый шаг под замком заново проверяет, что робот включён и настроен (`Worker.active`), и перечитывает
  сделку, — выключение посреди прохода останавливает оставшуюся очередь.

Проходы целиком (`tick`, `run_step`) не идут одновременно — у них свой замок `_pass`.

Эти замки — внутри одного процесса. Между процессами — файловый замок `db.service_lock` (`fcntl.flock` на
`<база>.lock` рядом с базой): сервис `run` держит его, пока работает, `once` и `process` — на время своей
работы. Занят — команда не запускается (код выхода 1, «остановите сервис или нажмите кнопку в панели»):
второй процесс со своим `Worker` отправлял бы и писал статусы мимо замка сервиса. `check`, `backup` и
команды пользователей замок не берут.

### Статусы сделки (`deals.status`)

| Статус | Значение |
|---|---|
| `new` | увидели, ещё не написали (или упали и повторим) |
| `pending_first` | Орбита ответила 202 (`pending_at`): сообщение могло уйти, ждём вебхук `message.sent` / `message.failed`. На `message.sent` `first_sent_at` — время отправки из события (нет — `pending_at`); если клиент уже написал в этот диалог (`message.received`, принятый после `pending_at`, пока номер диалога был неизвестен), — сразу `replied`. Исход и эта сверка —
одна транзакция до комментариев и возврата этапа: повтор события после обрыва ничего не теряет |
| `sent_first` | первое сообщение ушло, ждём ответа |
| `sent_followup` | напоминание ушло; через `followup_hours` — итог `replied` или `no_reply` |
| `replied` | клиент ответил; поля `reply_due_at` / `reply_sent_at` — ответ по шаблону |
| `no_reply` | не ответил: напоминание выключено или клиент молчит и после него |
| `no_messenger`, `no_phone` | этап сделки сменён на «Не нашёл мессенджер» |
| `skipped` | сделка закрыта, другая воронка, старше 48 ч или остановлена вручную |
| `needs_check` | не уверены, ушло ли сообщение, или Орбита сообщила, что сообщение не доставлено (`message.failed`) — нужен человек; робот не повторяет |
| `error` | 5 ошибок подряд — нужен человек. Счётчик `attempts` обнуляется, когда сделка сменила статус |

Сбой шага по сделке (Битрикс или Орбита недоступны, отказ Орбиты) — попытка: `attempts` растёт, следующая —
не раньше `next_attempt_at` (пауза 2, 4, 8, 16 минут — `RETRY_PAUSE`), пятая подряд → `error`. Если Орбита
назвала срок — 429 с `Retry-After`, `idempotency_in_progress` с `Retry-After`, `telegram_flood_wait` с
`retry_after`, суточный лимит `daily_send_limit_exhausted` (до полуночи UTC) или `telegram_search_limit_exhausted`
(до полуночи UTC — момент сброса в спецификации не назван, это допущение), — сделка ждёт этот срок, попытка
не тратится (в журнале «отложено»). При «не найден» в одних каналах и сроке в других срок берётся ближайший,
если его назвали все непроверенные каналы. Сбой одного шага прохода (например, опроса Битрикса) пишется
в лог и не отменяет остальные шаги.

«Повторить» в панели — `Worker.retry()`: статус `new`, если первое сообщение не ушло (`first_sent_at` пусто),
иначе `sent_first` / `sent_followup` / `replied` — с того места, где робот остановился. Номер повтора шага, с которого
продолжает робот, растёт и входит в ключ идемпотентности (см. «Защита от дублей»). При возврате в `new`
растёт `retry_n`, пишется `retried_at` (48 ч считаются от более позднего из `created_at` и `retried_at`), а
проверка этапа «Не нашёл мессенджер» в `first_contact` пропускается — этот этап ставил сам робот.

Возврат этапа. Перенося сделку на «Не нашёл мессенджер» (`_no_messenger`), робот запоминает её этап до
переноса в `stage_before` — до вызова Битрикса, чтобы обрыв между переносом и записью статуса не потерял
прежний этап (если сделка уже стояла на этом этапе — прежнее значение не затирается; сделка `new` с
`stage_before` на этом этапе — перенос робота, а не менеджера, и он не мешает следующей попытке). Когда
после «Повторить» первое сообщение ушло (201 или `message.sent` по 202), `_restore_stage` перечитывает
сделку: она всё ещё на «Не нашёл мессенджер» — возвращает на `stage_before`, комментарий в ленту; менеджер
уже сам перенёс её на другой этап — не трогает. `stage_before` пуст (сделка перенесена версией до
22.10.2026) — этап не трогается. Возврат — сохранённая работа: пока `stage_before` не пуст при заполненном
`first_sent_at`, его доделывает шаг прохода `stages` (после перезапуска и после сбоя Битрикса — с паузой
2, 4, 8, 16 минут, `stage_attempts` / `stage_retry_at`). Отправка при этом не повторяется. Пятый сбой
подряд — запись в журнал, комментарий «верните вручную», `stage_before` стирается.

### Защита от дублей

- У каждой отправки в Орбиту есть `Idempotency-Key` (`deal-<id>-first-<телефон>[-r<retry_n>]-<канал>`,
  `deal-<id>-followup[-r<followup_retry_n>]`, `deal-<id>-reply[-r<reply_retry_n>]`). Повтор с тем же ключом
  не отправит сообщение второй раз. Поэтому обрыв связи с Орбитой — обычная повторяемая ошибка. Ручной
  «Повторить» добавляет `-r<n>` к ключу того шага, с которого робот продолжит: первое сообщение (`retry_n`,
  возврат в `new`), напоминание (`followup_retry_n`, возврат в `sent_first`), ответ по шаблону
  (`reply_retry_n`, возврат в `replied`, если ответ не ушёл, — он планируется заново). Это новая отправка:
  со старым ключом Орбита вернула бы прежний исход, а при изменённом шаблоне — `idempotency_key_reused`.
  Ключи сделок, начатых до обновления, не меняются (номера повторов шагов — 0).
- Намерение напоминания и ответа по шаблону — `followup_key` / `reply_key`: ключ пишется до запроса и
  стирается только при определённом отказе (отказ Орбиты 4xx, `message.failed`). Исход неизвестен (сбой
  связи, 5xx, непредвиденный сбой, 202 без подтверждения) — ключ остаётся, и следующая отправка шага, в том
  числе после «Повторить», идёт **тем же** ключом: если прошлое сообщение дошло, Орбита второе не отправит.
  Новый `-r<n>` «Повторить» выпускает, только когда ключа нет — прошлая попытка точно не ушла.
- 202 на напоминание и ответ по шаблону (для WhatsApp и Max — обычный ответ: «команда передана») — сообщение
  могло уйти, исход придёт вебхуком. `OrbitaAPI.send_reply` возвращает статус и `request_key`; он
  сохраняется в `followup_request_key` / `reply_request_key` до вебхука. `message.sent` — ключ стирается,
  в журнале «мессенджер подтвердил доставку». `message.failed` — шаг не сделан: `needs_check`, причина в
  `last_error` и журнале, комментарий в сделку; `followup_sent_at` / `reply_sent_at` стираются, у ответа
  по шаблону `reply_due_at` остаётся (ответ ещё нужен). Так же — из `needs_check` по таймауту и из
  `no_reply`: итог «не ответил» по недоставленному напоминанию снимается. Пришёл, когда клиент уже ответил
  или сделку остановили, — только запись в журнал. Пока напоминание не подтверждено, итог «не ответил»
  (`after_followup`) не выносится. Вебхука нет 30 минут — `needs_check` (`Worker.send_timeout`), ключи
  остаются: поздний `message.sent` возвращает сделку в `sent_followup` / `replied`, а «Повторить» снова
  отправляет шаг **тем же** ключом (Орбита вернёт исход прошлого запроса, второго сообщения не будет).
  Поэтому без вебхуков каждое напоминание и ответ по шаблону, на которые Орбита ответила 202, через 30
  минут становятся «проверить вручную» — как и первое сообщение.
- Вебхуки Орбиты — durable inbox. Для Орбиты ответ 2xx значит «доставлено», повтора не будет, поэтому
  `/orbita/webhook` до ответа сохраняет событие целиком в `orbita_events` (`state='new'`, номер события —
  ключ дедупликации; повтор доставки с тем же номером отвечает `duplicate`). Событие без номера
  сохраняется под своим (`local-…`). Обработка — `Worker.process_inbox()`: сразу в фоне и на каждом
  проходе (шаг `events`, идёт и при выключенном роботе). `done` ставится только после успешной обработки;
  сбой пишется в журнал («Орбита: ошибка обработки события») и в лог, событие остаётся в очереди до
  следующего прохода, после 5 сбоев — `failed`. Остановка сервиса посреди обработки оставляет событие
  в очереди — его подхватит первый проход после запуска. Обработка идемпотентна: каждое действие
  проверяет статус сделки. Строки старых версий (без тела) при обновлении считаются `done`. Обработанные
  (`done`) события старше 30 дней (`EVENTS_KEEP`, по `done_at`, у старых строк — по `at`) удаляет шаг
  `cleanup`: дубли доставки и сверка ответа клиента до подтверждения первого сообщения смотрят только
  недавние события. `new` и `failed` не удаляются. Индексы `orbita_events` — `db.INDEXES`, создаются после
  `MIGRATIONS`.
- Намерение первой отправки. Каналы перебирает сам робот (`Worker.first_contact`, по телефонам и по
  порядку каналов из настроек; клиент Орбиты — `OrbitaAPI.start_dialog`, один канал за запрос). Перед
  каждым `POST /dialogs` в сделку пишется намерение: `intent_phone`, `intent_channel`, `intent_key`;
  стирается оно, когда исход определён — ответ 201/202/«не найден»/«не проверен»/400 или отказ 4xx, по
  которому точно ничего не ушло. На 201/202 намерение стирается той же записью, что ставит `sent_first` /
  `pending_first`: обрыв процесса между ними не оставит сделку `new` без намерения. Сбой связи, 5xx и `idempotency_in_progress` намерение оставляют, и
  следующая попытка сначала повторяет **тот же** запрос (канал, ключ, текст `first_text`): Орбита вернёт
  исход первого вызова. Канал намерения сейчас не подключён → `needs_check` (в другой канал писать нельзя —
  клиент получит два первых сообщения). «Повторить» из `needs_check` намерение стирает: человек проверил
  переписку, панель предупреждает о втором сообщении.
- Неизвестный исход (`UnknownOutcome`) → `needs_check`, без повтора.
- «Номера нет в мессенджере» — только если **все** выбранные каналы ответили «не найден». Выбранный, но не
  подключённый канал номер не проверял; он, как и канал, не смогший проверить номер (лимит, сбой шлюза),
  даёт ошибку с повтором, а не перенос на этап.
- Орбита не приняла номер (400 `invalid_request` на «написать первым») — номер пропускается, пробуется
  следующий телефон контакта; не принят ни один — как «нет телефона» (`no_phone`, этап «Не нашёл мессенджер»).
- Сделки старше 48 часов не трогаем. Возраст — от `DATE_CREATE` сделки в Битриксе (пока Битрикс не
  спрошен или даты нет — от `created_at`, момента, когда робот увидел сделку) или от ручного повтора /
  «Взять в работу» (`retried_at`), что позже.
- Граница включения `kv.start_deal_id` — последняя сделка Битрикса в момент включения; не меняется до
  следующего включения (в отличие от курсора опроса `last_deal_id`). Событие Битрикса о сделке, которой
  нет в базе и чей ID не больше границы, робот пропускает: она создана до включения. «Взять в работу» в
  панели (`Worker.take`) — явный путь, граница ему не мешает. Установкам, включённым до появления границы,
  она при запуске берётся из `last_deal_id`.

## Настройки

- `Env` (`config.env()`) — из переменных окружения / `.env`: `DB_PATH`, `PUBLIC_URL` или `DOMAIN`, `PORT`,
  `POLL_SECONDS`, `DRY_RUN`, `HOST` (по умолчанию `127.0.0.1`), `FORWARDED_ALLOW_IPS` (чьим `X-Forwarded-*`
  верить, по умолчанию `127.0.0.1`). В Docker-образе `HOST=0.0.0.0` и `FORWARDED_ALLOW_IPS=*`: порт контейнера
  открыт только для самого сервера, снаружи — только через Caddy.
- Воронка: `Settings.category` — выбранная воронка или `"0"` (основная), если не выбрана. Робот работает
  только с ней.
- `Settings` (`config.load(db)`) — из таблицы `settings` (ключ → JSON). Меняются в панели через
  `worker.save(**поля)`: значение пишется в базу и сразу действует. Если меняется адрес Битрикса или ключ
  Орбиты, клиенты пересоздаются (`worker.reconnect()`).

Чтобы добавить настройку: поле в `Settings` со значением по умолчанию → поле формы в `ui_settings.py` →
использование в `worker.py`. Миграция не нужна: отсутствующий ключ берётся из значения по умолчанию.

При самом первом запуске, если в базе нет настроек, `config._seed_from_env()` берёт их из старых
переменных окружения (`BITRIX_WEBHOOK`, `ORBITA_API_KEY`, …) — для установок, настроенных до панели.

## База

Схема — `db.SCHEMA`, новые колонки — список `db.MIGRATIONS` (добавляются при запуске сами).
Чтобы добавить колонку в существующую таблицу, допишите строку в `MIGRATIONS`.

## Как подключить другую CRM

`Worker` вызывает у `self.bitrix` только эти методы:

```python
async def get_deal(deal_id: int) -> Deal            # Deal: id, title, stage_id, stage_semantic ("P" — в работе),
                                                     #       category_id, contact_id, created_at (aware или None)
async def get_contact(contact_id: int) -> tuple[str, list[str]]   # имя, телефоны в виде +7…
async def deal_ids_after(last_id: int, category_id: str | None) -> list[int]   # новые сделки по возрастанию
async def max_deal_id() -> int
async def set_stage(deal_id: int, stage_id: str) -> None
async def comment(deal_id: int, text: str) -> None
```

Для страницы настроек — ещё `categories()` и `stages(category_id)` (списки пар `(id, название)`).
Списочные методы Битрикса отдают по 50 строк; `Bitrix.call_all` читает все страницы по `next`
(`deal_ids_after`, `stages`).

Чтобы подключить, например, amoCRM:
1. Напишите класс с этими методами (`src/first_contact/amocrm.py`).
2. В `Worker.reconnect()` выберите класс по настройке (например, `crm = "bitrix" | "amocrm"`).
3. Добавьте приём вебхука новой сделки в `app.py` по образцу `/bitrix/deal-add`.
4. Добавьте блок настроек в `ui_settings.py`.

В amoCRM ID сделок тоже растут, так что опрос по `last_deal_id` подходит.

## Как добавить свой шаг

Пример: «двигать сделку на этап „Написали“ после первого сообщения».
1. `config.Settings`: `stage_after_first: str = ""`.
2. `worker._mark_sent_first`: `if self.s.stage_after_first: await self.bitrix.set_stage(...)`.
   Метод синхронный — вызывайте из `first_contact` после `_mark_sent_first`.
3. `ui_settings.bitrix_section`: ещё один `<select>` с этапами, сохранение в `save_bitrix`.
4. Тест в `tests/test_worker.py`.

## API Орбиты

Публичная спецификация: `https://crm.my-orbita.ru/api/public/v1/openapi.json` (копия в `docs/`).

Что использует робот:
- `GET /account`, `GET /channels`;
- `POST /dialogs` — «написать первым» (по одному каналу за запрос);
- `POST /dialogs/{id}/messages` — ответ в диалог;
- `GET /dialogs/{id}/messages` — история (только направление и время, без текста). Лента — новые первыми,
  страницами по `next_cursor`; `OrbitaAPI.history(dialog, since)` читает страницы, пока не дойдёт до
  `since` (первое сообщение робота) с запасом `CLOCK_SKEW`. Время без смещения считается UTC.
  Сообщение без `sent_at` нельзя расположить относительно первого сообщения: ответом клиента оно не
  считается, молчанием тоже. Если кроме него входящих после первого нет — «не понять»
  (`client_replied` → `None`): напоминание не уходит, сделка — `needs_check`;
- вебхуки, подпись `X-Orbita-Signature: v1=HMAC-SHA256(секрет, "<timestamp>.<тело>")`.

Коды «номера нет»: `not_on_whatsapp`, `max_not_found`, `telegram_recipient_not_found`,
`telegram_recipient_refused`.

Лимиты: 600 запросов в минуту и 1000 отправок в сутки на ключ, поиск в Telegram — 30 номеров в сутки
на сотрудника.

MCP Орбиты робот не использует: «написать первым» есть только в REST API.
